# Patches

Every file in this directory is a unified diff against the pinned upstream
commit listed in `Build/versions.env`. The build script applies them in
lexical order with `git apply --3way` before configuring CMake. Each patch is
kept as small as possible so that it can be proposed upstream unchanged.

Upstream status: "to be proposed" means the patch has not been submitted yet. Every patch is written against upstream style so it can be submitted as is.

There is no 0013: it required an IP address SAN for TLS servers given as an IP literal, which libre does itself since v4.12.0 (baresip/re#1618).

| `0001-baresip-account-contact-uri-params.patch` | baresip v4.13.0 | libre already supports Contact URI parameters on REGISTER through `sipreg_set_contact_params()`, but baresip never calls it and offers no public setter. The patch adds `account_set_contact_params()` / `account_contact_params()` and wires the value into `reg_register()` so every REGISTER (initial, auth retry, refresh, re-register after a token update, unregister) carries the parameters inside the Contact URI. An error from `sipreg_set_contact_params()` stops `reg_register()`. `ua_set_contact_params()` does not send a second REGISTER while one that baresip started is unanswered: two challenged requests were reported as a failed registration (401), and the first request kept a pointer into the registration client that libre wrote to after the client was freed. The new parameters are stored at once, so an authentication retry already carries them, and the REGISTER is sent when the response arrives. libre's own periodic refresh is not visible to baresip and is not covered. | to be proposed |
| `0002-baresip-avcapture-cmake-ios.patch` | baresip v4.13.0 | `modules/avcapture/CMakeLists.txt` only enables the module when `CMAKE_SYSTEM_NAME` is `Darwin`. An iOS cross-build sets `CMAKE_SYSTEM_NAME=iOS`, so the AVFoundation capture module was silently dropped from iOS builds. The patch accepts `iOS` as well. The module also contains macOS-only API (`AVCaptureScreenInput`), handled by 0003, and uses manual reference counting; see the feasibility report for why BaresipKit ships its own capture source anyway. | to be proposed |
| `0003-baresip-avcapture-ios-screen-input.patch` | baresip v4.13.0 | With 0002 the module is compiled for iOS and fails against the iOS SDK: `'AVCaptureScreenInput' is unavailable: not available on iOS` (`avcapture.m:26`, `:216`, `:316`). The patch guards the screen-capture parts with `TARGET_OS_IPHONE`, in the style the file already uses for the macOS-only presets: the ivar is typed `AVCaptureInput *` on iOS, the two `AVCaptureScreenInput` allocations and the `screen` device registration are compiled only for macOS. On iOS, opening `screen` returns no source instead of crashing; macOS behaviour is unchanged. | to be proposed |
| `0004-re-tls-verify-server-handler.patch` | libre v4.13.0 | libre verifies server certificates with OpenSSL's default callback and offers no hook for the client side. The patch adds `tls_set_verify_server_handler()`, which receives OpenSSL's pre-verification result, the chain depth and the certificate in DER form for every certificate of the server chain. BaresipKit uses it for SPKI SHA-256 pinning (`Core/src/bsk_tls.c`). Plain C types only, no OpenSSL types in the public API. | to be proposed |
| `0005-baresip-ice-module-events.patch` | baresip v4.13.0 | The ICE module logs state changes but emits no events, so an application cannot learn the ICE state or the selected candidate pair without parsing logs. The patch emits `module_event("ice", ...)` for gathering, checking, connected (with local/remote candidate types and addresses) and failed, keyed by the SDP media pointer so the application can map it to a call. | to be proposed |
| `0006-baresip-start-media-after-mnat-with-optional-menc.patch` | baresip v4.13.0 | When a media encryption is configured, `stream_mnatconn_handler()` only started the media encryption after the media NAT connected and never started audio or video. With optional SDES-SRTP that the peer declines, and ICE completing after the call was answered (typical for TURN relay), the call stayed silent: no RTP was ever sent. Found by the TURN relay integration stage. The patch starts the streams whenever they are ready; encryptions that wait for a secure state (DTLS-SRTP) are unaffected because `stream_is_ready()` still returns false until they are secure. | to be proposed |
| `0007-baresip-ice-turn-over-tcp-tls.patch` | baresip v4.13.0 | The ICE module allocated relayed candidates over UDP only, so `turn:...?transport=tcp` and `turns:` were unusable with ICE, which matters on networks that block UDP. The patch connects to the TURN server over TCP (and TLS for `turns:`, verified with the SIP TLS context), allocates the relay on that connection, forwards the component's outgoing packets through it with a UDP helper and injects relayed data back into the UDP socket, reusing the stream framing of baresip's `turn` module. The receive handler holds a reference to the media while it runs, because the ICE handlers it calls can close the media. Packets are never sent on the plain UDP socket in this mode: without a TURN connection they are dropped, so the local address is not revealed, and packets without enough headroom for the TURN header are copied. For `turns:` the connection is torn down if TLS cannot be set up, and a relay is never allocated over a connection without TLS. The receive buffer keeps at most one incomplete message, and a ChannelData message is consumed only once its padding has arrived. When TURN runs over TCP/TLS the session uses the relay-only ICE policy, because host and server-reflexive paths cannot be assumed to work on such networks. A connection that is refused, fails the TLS handshake or the certificate check, is closed, gets an error for the allocation or does not finish the allocation within 10 seconds ends the gathering of its component with an error, so the call attempt fails instead of waiting forever. If the connection is lost later, the refresh fails or the stream cannot be parsed, the connection is closed and the module emits `ice,failed` once for the media line; an ICE restart (0008) then connects and gathers again. | to be proposed |
| `0008-baresip-ice-restart.patch` | baresip v4.13.0 | A network change re-INVITEd ICE calls with the old credentials and candidates, which are bound to the previous network, so media did not recover. The patch adds an optional `restarth` hook to `struct mnat` and a public `call_restart_mnat()`. `call_reset_transp()` uses the hook when available: the ICE module creates new `ice-ufrag`/`ice-pwd`; if the local address changed or a TURN connection was lost (0007) it drops its STUN/TURN state, gathers again and the existing "media-nat established" path sends the re-INVITE once gathering completes, otherwise it keeps the gathered candidates and TURN allocations (TURN servers reject a second allocation from the same 5-tuple) and re-INVITEs right away; the connectivity checks start when the answer carries the peer's new credentials and are repeated up to five times, one second apart, if they fail, because a peer can still reject the first checks while it switches to its new credentials. An incoming offer with a new `ice-ufrag` restarts ICE on the answering side with new credentials and the already gathered host, server-reflexive and relayed candidates, so the answer is complete without waiting. Without negotiated ICE the call falls back to the plain re-INVITE. A restart that fails does not close the call: if gathering cannot start or fails, if the gathered candidates cannot be reused and gathering again fails, or if the peer does not answer with new credentials within 15 seconds, the module emits `ice,failed` for every media line, sends no re-INVITE with the half-reset state and accepts another restart. The STUN/TURN server address from the start of the call is reused; it is not resolved again. | to be proposed |
| `0009-baresip-video-set-bitrate.patch` | baresip v4.13.0 | baresip fixes the video encoder bitrate when the encoder is created, so an application cannot react to packet loss without renegotiating. The patch adds `video_set_bitrate()`, which stores the new target and passes it to the running encoder through the codec's update handler, and `video_bitrate()` to read it. The send pacer keeps the configured rate as its ceiling. | to be proposed |
| `0010-baresip-vidfilt-skip-unused-direction.patch` | baresip v4.13.0 | A video filter that handles only one direction still got an empty entry in the other direction's filter list, and a non-empty decoder list makes the receiver copy every decoded frame before display. BaresipKit's local-preview tap is encode-only, so every remote frame was copied and the decoder's `CVPixelBuffer` could not reach the renderer. The patch adds a filter to the encoder or decoder list only when it handles that direction. | to be proposed |
| `0011-baresip-audio-natpinhole-recvonly.patch` | baresip v4.13.0 | The `natpinhole` account option sends empty RTP packets while a stream only receives, so that media relays which learn the endpoint from the first packet (rtpengine) and NATs forward the peer's media. Only video used it, so a receive-only early media preview without ICE stayed silent behind such relays. The patch opens the pinhole for receive-only audio too; it stops when the first RTP packet arrives or the direction changes. | to be proposed |
| `0012-baresip-picture-update-sip-info.patch` | baresip v4.13.0 | Some video endpoints, such as door stations, send a key frame only when asked with a SIP INFO `picture_fast_update` (RFC 5168) and ignore RTCP PLI/FIR. The patch answers such an INFO by requesting a key frame from the encoder, adds `call_send_picture_update()`, and the `vfu_info` account parameter that also sends the request over SIP INFO whenever the video receiver asks for a new picture (`video_set_picup_handler()`). | to be proposed |
| `0014-baresip-avcapture-ios16.patch` | baresip v4.13.0 | For an iOS deployment target below 17.0 the camera discovery listed `AVCaptureDeviceTypeExternalUnknown`, which exists only on macOS, so the module did not compile. External cameras exist on iOS only from 17.0; before that the patch lists the built-in wide-angle cameras alone. | to be proposed |
| `0015-re-sipreg-contact-params-leak.patch` | libre v4.13.0 | `sipreg_set_contact_params()` overwrote the stored Contact parameters without freeing them and returned `EINVAL` for `NULL`. Every push token update leaked the previous string, and clearing the parameters failed, so no REGISTER went out. The patch frees the old value and accepts `NULL` to clear; it also extends libre's sipreg test. | to be proposed |
| `0016-baresip-refer-requires-established-call.patch` | baresip v4.13.0 | `sipsess_refer_handler()` accepted a REFER in every call state and moved the call to the transfer state. A peer could send INVITE and then REFER while the callee's phone was still ringing: the application was told to dial the transfer target, and the ringing call could no longer be answered because it had left the incoming state. The patch answers a REFER with 403 unless the call is established. | to be proposed |
| `0017-baresip-uag-wss-tls-accessor.patch` | baresip v4.13.0 | The secure WebSocket transport has its own TLS context, which only receives the CA file and path of the configuration. An application that configures TLS through `uag_tls()` (CA in memory, client certificate, verify handler) had no way to do the same for WSS. The patch adds `uag_wss_tls()`. | to be proposed |
| `0018-re-tls-trust-handler.patch` | libre v4.13.0 | OpenSSL can only verify a server against certificates loaded into its own store, and iOS offers no way to read the system roots. The patch adds `tls_set_trust_handler()`: for verified client connections the handler is asked when OpenSSL cannot anchor the chain in its store, and replaces OpenSSL's verification when the store is empty and no CA directory was added (the certificates of a directory are loaded on demand, so the store alone does not show them). It receives the host name or IP address and the chain in DER form, so the application can evaluate it with the platform trust store (SecTrust on Apple platforms). | to be proposed |
| `0019-re-sipreg-replace-pending-request.patch` | libre v4.13.0 | `sipreg` sent a new REGISTER while an earlier one was unanswered, for example when `sipreg_send()` is called during a refresh or the refresh timer fires during a request the application started. Both requests then shared the client's request pointer: the first response cleared it while the second request was still pending, so the response handler ran twice and a client released at that moment was freed while a request still pointed into it. The patch drops the pending request before sending a new one; libre's test suite gets a case for it. | to be proposed |
| `0020-re-sip-request-release.patch` | libre v4.13.0 | A stateful SIP request that its owner released before a provisional response stayed allocated until `sip_close()`: its destructor took a new reference for the cancellation, and `sip_request_cancel()` dropped the client transaction that would have released it. Every REGISTER replaced by patch 0019 and every registration removed during a pending REGISTER kept about 2.5 kB until the engine stopped. A request still waiting for its address lookup was even sent after the release. The patch keeps the request only while a transaction waits for the final response and frees it otherwise; libre's test suite gets a case that counts the allocated blocks. | to be proposed |
| `0021-re-sipreg-release-unregisters-at-once.patch` | libre v4.13.0 | A registration client that was released during an unanswered REGISTER waited for the response and only then sent the REGISTER with `expires=0`. baresip replaces the client on every `ua_register()`, so after a second registration, a network change or a push wake-up during an unanswered REGISTER the old client removed the binding after the new client had registered: the application was registered and the registrar had no binding. The patch sends the removing request at once, in place of the unanswered one (patch 0019), so it leaves before the REGISTER of the new client. A released client also keeps the Contact address it registered with, so a request repeated after a change of the local address cannot name the address of the new client. libre's test suite gets a case for the order. | to be proposed |
| `0022-re-tcp-close-on-recv-error.patch` | libre v4.13.0 | `tcp_recv_handler()` logged a failed `recv()` and returned without closing the connection, except on Windows. The socket stays readable, so the handler runs again at once: on iOS, a TLS connection that the system dropped while the app was suspended returned `ENOTCONN` tens of thousands of times in under a second when the app came back, until a send failed. The patch closes the connection with the error, as for a reset on Windows, and keeps going on `EAGAIN`, `EWOULDBLOCK` and `EINTR`. The full libre regular test suite passes with it. | to be proposed |
| `0023-baresip-stream-send-on-hold.patch` | baresip v4.13.0 | A held stream offers `sendonly` but `stream_send()` drops every packet, so a phone cannot play music on hold to the other side, which liblinphone does with its play file and which PBXs that pass the hold through (instead of playing their own music) rely on. | `0024-re-sipsess-session-timers.patch` | libre v4.13.0 | libre and baresip have no SIP session timers (RFC 4028), and some providers and PBXs end calls without them or reject an INVITE that does not support them. The patch adds `sipsess_set_timer()` for the sessions of a socket: an INVITE offers `Supported: timer`, `Session-Expires` and `Min-SE`; a 2xx to an INVITE whose caller supports timers carries `Session-Expires` with the refresher (the caller unless it says otherwise) and `Require: timer`; a 2xx to an INVITE without timer support carries none. The refresher sends an UPDATE without a body at half the interval, or a re-INVITE without an offer when the peer's `Allow` has no UPDATE, and every re-INVITE or UPDATE either side sends carries the current interval and refresher; a refresh that is not answered leaves the expiry timer running. The other side ends the session with BYE (`ETIMEDOUT`) when no refresh arrived `min(32, interval / 3)` seconds before the interval ran out, and the refresher does the same when it could not send a refresh by then, for example after losing its transport. An INVITE, re-INVITE or UPDATE whose interval is below this side's `Min-SE` is answered with 422 before the application sees it; a 422 from the peer raises the interval to its `Min-SE` and sends the INVITE, re-INVITE or UPDATE again. `sipsess_timer()` returns the negotiated interval and whether this side refreshes. Without `sipsess_set_timer()` nothing changes. libre's test suite gets seven cases with two SIP stacks: refresh with re-INVITE and with UPDATE, expiry with BYE, a refresher that cannot send, a caller without timer support, a 422 sent below Min-SE and a 422 received. | to be proposed |
| `0025-baresip-session-timer-config.patch` | baresip v4.13.0 | Exposes patch 0024 in baresip's configuration: `sip_session_expires` (seconds, 0, the default, keeps session timers off) and `sip_min_se` (default 90). `ua_init()` passes them to `sipsess_set_timer()`, and with session timers on every user agent lists the `timer` extension, so it is in the `Supported` header and an INVITE with `Require: timer` is accepted instead of answered with 420. | to be proposed |
| `0026-baresip-audio-set-source-without-device.patch` | baresip v4.13.0 | Since v4.13.0 `audio_set_source()` copies the device name with `str_dup()`, which fails with `EINVAL` for a `NULL` device, so a source registered by the application (BaresipKit's music on hold) can no longer replace the microphone. The patch copies the device name only when there is one. | to be proposed |
| `0027-baresip-ice-relay-send-on-main-thread.patch` | baresip v4.13.0 | baresip's audio and video threads sent RTP of a relayed component into the TURN client on their own thread: over UDP into its channel and permission lookups, over TCP or TLS (0007) into `turnc_send()`, `tcp_send()` and `SSL_write()`, while the re thread used the same TURN client and OpenSSL object for connectivity checks, ChannelBind, refreshes and reads. Under load `SSL_write()` failed with `SSL_ERROR_SSL` and the call lost its relay. The patch registers a helper above the ICE layer and below SRTP for every component that gathers a relay; packets from another thread are copied into a mutex-guarded queue of at most 256 packets and sent from the re thread, woken through an `mqueue`, down through the ICE and TURN helpers. The queue is emptied when the media is destroyed, after the sending threads have been joined. | to be proposed |
| `0028-baresip-call-dtmf-via-info.patch` | baresip v4.13.0 | A call reports a received DTMF digit through the same handler and events whether it came as an RTP telephone event or in a SIP INFO request, so BaresipKit could not set `viaSIPInfo` for received digits. The patch records the source of the last digit and adds `call_dtmf_via_info()`; the end of a SIP INFO digit, which its timer reports later, keeps the SIP INFO flag. | to be proposed |

## Verifying a patch

```bash
for patch in Patches/*-baresip-*.patch; do git -C Build/.deps/baresip apply --check --reverse "$patch"; done
for patch in Patches/*-re-*.patch; do git -C Build/.deps/re apply --check --reverse "$patch"; done
```

After a build, `--reverse --check` confirms that every patch is applied to the checked-out sources.
